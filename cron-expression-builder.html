Cron Expression Builder — free, instant, private

Build 5-field cron expressions visually, get a plain-English description and the next 5 run times — or paste one to decode it.

Quick answer

A cron expression is five space-separated fields — minute, hour, day-of-month, month, day-of-week — that define a recurring schedule: `*/5 * * * *` runs every 5 minutes, `0 3 * * 1` runs every Monday at 3 AM. This builder edits all five fields visually, translates the schedule into plain English, and computes the next five actual run times from your clock.

How the cron expression builder works

Fields: minute (0–59) · hour (0–23) · day of month (1–31) · month (1–12) · day of week (0–6, 0 = Sunday)  ·  Syntax: *, values, ranges (1-5), steps (*/10), lists (1,15,45)

Every field accepts four kinds of values:

  • * — every possible value ("every minute", "every hour")
  • A single number — only that value (30 = at minute 30)
  • A range — 1-5 means 1,2,3,4,5 (classic: 1-5 = weekdays in the dow field)
  • A step or list — */10 means every 10th value; 0,15,30,45 means those four values

You can combine them per field with commas: 0 9,17 * * 1-5 = at 9:00 and 17:00 on weekdays. Two classic gotchas: day 0 and 7 both mean Sunday in the weekday field, and if BOTH day-of-month and day-of-week are restricted (not *), cron fires when either matches — that surprises almost everyone once.

Frequently asked questions

Does this support 6-field cron (with seconds)?

No — this builder targets the standard 5-field UNIX/crontab format used by Linux crontab, most job schedulers and tools like GitHub Actions' cron trigger. Quartz-style 6-field expressions (with a leading seconds field) are a different dialect.

What timezone do the next run times use?

Your browser's local timezone — the same clock your device uses. Note that servers usually run UTC, so a 'daily at 3 AM' job on a UTC server fires at different local times; schedule against the server's timezone, not yours.

Why does my day-of-month + day-of-week combo fire too often?

Standard cron treats two restricted day fields as OR, not AND: 0 0 13 * 5 fires on the 13th AND on every Friday, not only Friday-the-13th. That is defined POSIX behavior, not a bug — restrict only one day field to avoid it.
